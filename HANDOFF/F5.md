## 1. The brief's premise, tested first

> *"The page's RBAC gate in `components/finance/finance-scope.ts` and the repository's role-level
> gate in `lib/finance-repository.ts` disagree about who may read what… One of the two gates is
> wrong about the permission matrix; find which by reading W1-B's matrix as the authority."*

**Neither gate is wrong. They do not disagree.** I checked before changing anything, because a fix
aimed at the wrong cause is worse than no fix — and the proposed fix was to narrow or widen a
permission, which would have changed real authorisation to chase a symptom.

`scripts/finance-gate-parity.mts` transcribes W1-B's matrix longhand — deliberately not derived
from `rbac.ts`, which would make it a tautology — and asserts both gates against it:

```
1. The page gate reproduces W1-B's matrix exactly          33 cells
2. The repository gate never refuses a role the page admits 17 cells
50 pass · 0 fail
```

The claim collapses on one reading of the repository. It has exactly **one** predicate that denies:

```ts
/** Mirrors `is_finance_visible_role()`: FALSE for anon, `guest` and `child_guest`. */
function isFinanceVisibleRole(role) { return role !== undefined && role !== "guest" && role !== "child_guest" }
```

`guest` and `child_guest` hold none of the three view permissions, so the page refuses them first.
Every other role passes. The second predicate, `canReadCompanyFinance` (level ≥ accountant), does
not deny anything — it **widens** a scope from own-rows to company-wide:

```
admin      90  -> company-wide books      staff             40  -> own rows only
manager    70  -> company-wide books      service_provider  30  -> own rows only
accountant 60  -> company-wide books      owner  20 · tenant 10 · child_* -> own rows only
```

F1-001's table reads that row as "the repository gate says no" for staff, owner, tenant and the
children. It says *"scope this caller to their own rows"*. Those are different answers, and the
design intends the second — `finance-scope.ts`'s own header says so: *"`owner` holds `finance:view`
for its own statement. `canViewInternalFinance()` is the separate gate on the company books."*

**Nothing was widened, nothing was narrowed, and no permission changed.**

## 2. What actually produced the 500s

A repository refusal had **no handler**. `withRepository()` throws when Supabase is configured and
a query fails, and an unhandled throw in a Server Component is an HTTP 500.

Captured on this branch before the fix, `admin`, `/de/dashboard/wallet`:

```
[repository:finance.getPaymentTransactions] {
  code: '42501',
  message: 'permission denied for table payment_transactions',
  hint: 'Grant the required privileges to the current role with:
         GRANT SELECT ON public.payment_transactions TO anon;'
}
⨯ Error [RepositoryError]: You do not have access to this data.
    at async o (.next/server/app/[locale]/dashboard/wallet/page.js)
  apiError: { code: 'forbidden', … }
-> HTTP 500
```

**The refused role is `anon`, not the application role.** That is the whole explanation, and it is
why the diagnosis went astray:

- `forbidden` is not a decision the repository's TS gate made. `lib/repository-base.ts` maps
  PostgREST **`42501`** to `forbidden`, so the refusal came from Postgres.
- The QA access-profile fixture sets an **application** role via cookie but never a **Supabase
  session**, so every query runs as `anon`, and `anon` holds no `GRANT` on `wallets` or
  `payment_transactions`.
- `admin` 500s in that fixture too — which no role-gate disagreement could ever produce, and which
  is the detail that falsifies the hypothesis outright.

### Why it was invisible until now, and why it is not a finance problem

While M-002 was live, every user resolved to `tenant`, so no role-specific path ran. F1 fixed that
and the class surfaced. It is not confined to finance: **any** RLS tightening or missing grant
reaches the same unguarded boundary on any page. §5 measures 24 more.

### What I deliberately did not do

**I did not add the missing `anon` grants.** `GRANT SELECT ON public.wallets TO anon` is exactly the
direction the brief forbids and W2-A already caught once on `leads`. `anon` **should** be refused
here. The defect is that the application answers a refusal with an error page.

## 3. The fix

`apps/web/components/finance/finance-read.ts` (new). Each read runs through `readFinance()`, which
classifies a failure instead of propagating it:

| Outcome | Rendered | Why apart |
| ------- | -------- | --------- |
| `forbidden` · `unauthorized` | the `AccessRefused` panel the pages already import | An answer. No retry helps |
| anything else | a distinct outage message | An outage. Retrying **is** the right advice |

Three properties worth stating:

- **It does not swallow the signal.** A refusal arriving in that catch means the RBAC gate admitted
  a caller the data plane then refused — a genuine divergence — so it is logged through W3-D's
  existing `logDeniedFinanceAccess` channel, structured and greppable, rather than disappearing
  behind a rendered panel. Non-refusals log the full cause; swallowing it would make the next one
  undiagnosable.
- **A surface refuses as a whole.** A wallet page rendering balances while silently dropping the
  movements it was refused is a screen that lies by omission, so `anyRefused()` covers the set and
  the log records which read caused it.
- **`API_ERROR_CODES` enumerates the frozen CONTRACTS §5 union**, so a code added there without a
  decision here is a compile error rather than a silent "unavailable".

`access-refused.tsx` gains `data-slot="access-refused"` as a test seam — see §6.

six 500s is now a rendered refusal in every cell.

### One thing the brief asked for that I did not change

> *"A role that may not read must get **403**, never 500, never a blank."*

**Every refusal renders the refusal panel. Every refusal is HTTP 200, not 403** — all 48 refusal
cells, both modes. That is the project's existing convention, not something this branch introduced:
W3-B's shell guard returns 200 with a `data-testid="dashboard-403"` panel, and its contract argues
the case (*"403, NOT a redirect"* is about the panel, not the status line). Changing the status code
would be a cross-cutting change to W3-B's contract affecting all 21 dashboard routes, so it is
raised in §7 rather than taken unilaterally. **The user-visible behaviour the brief wanted — a
refusal, never an error page, never a blank — holds in 66 of 66 cells.**

## 6. Four harness defects of my own, each caught before it became a finding

Recorded in full because two of them produced results that looked exactly like application bugs, and
one is the direct descendant of W5's stale-port mistake.

1. **The port guard rejected its own server. Twice.** `assertOwnPort()` compares the listening PID's
   command line against this worktree. The app directory reaches that command line in three
   spellings — `D:/azura-f5/…` from a bootstrap literal, `D:\azura-f5\…` from `next start`, and
   `D:\\azura-f5\\…` once JSON-escaped inside `node -e`. Two versions matched one spelling each and
   halted the run. It normalises separators now. **The guard is W5's lesson made mechanical, and it
   is staying** — a false alarm costs a minute; the failure it prevents cost W5 a pass.
2. **Session mode hand-assembled an `@supabase/ssr` cookie.** Every request 307'd to `/de/login` and
   the matrix read as **33 application failures**. The cookie format is `@supabase/ssr`'s to define,
   not a test script's to guess; it drives a real form login now.
3. **The refusal detector grepped for `"Kein Zugriff"`** and matched a per-KPI-card refusal on a
   fully-rendered admin page: **17 false failures**, every one of them a screen that was working.
4. **Fixing that to a structural check went too far the other way.** Accepting only
   `data-slot="access-refused"` missed every role W3-B's **shell** guard stops before the page runs
   — a second, equally valid refusal layer. It accepts both now.

Defects 2, 3 and 4 each produced a red matrix on a healthy application. That is the failure mode
this project keeps hitting, and the answer each time was to check what the page actually rendered
rather than to believe the harness.

## 9. The one-line answer

F1-001 was real, reproducible and worth fixing — but it was never a disagreement between two gates.
It was a repository refusal with nowhere to go, in a QA fixture that runs every query as `anon`.
The gates agree, 50 assertions deep; the finance surfaces now refuse in 66 of 66 cells instead of
erroring in six; and the same defect is sitting on 24 more cells across four other windows.

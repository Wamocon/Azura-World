## 1. The four, and what each one actually was

### M-005 — a raw message key where the demo-data warning should be

**Was.** `/dashboard/units` rendered the literal string
`common.dataSource.localSeedHint` at the top of the 656-unit inventory. The
control that tells a viewer the numbers are seed data was itself unreadable.

**Cause.** `common.notAvailable` and `common.dataSource.localSeedHint` existed in
no catalogue. next-intl renders the key path rather than throwing, so the page
looked fine to the build and broken to a person.

**Fixed by** adding both keys to all four catalogues, 1834 → 1836 paths each,
identical key sets.

**The class, not the instance.** Two is what one person found on one screen, so
the whole tree was scanned first: every `getTranslations`/`useTranslations`
variable resolved to its namespace, every `t("literal")` call resolved to a full
dotted path, every path checked against all four files.

```
scanned 1354 resolvable t(...) calls

MISSING KEYS  (used in source, absent from a catalogue)
  common.dataSource.localSeedHint    absent in all four
      app/[locale]/dashboard/units/page.tsx
  common.notAvailable                absent in all four
      app/[locale]/dashboard/units/page.tsx

all four catalogues carry the identical 1834 key paths
```

Exactly the two reported, nothing else, and no catalogue drift. After the fix
the same scan prints `no missing keys`.

**The wording is not new.** `common.notAvailable` reuses the four strings
`evidence.confidence.gap` already ships — "Keine Angabe" / "Not stated" /
"Belirtilmemiş" / "Нет данных", which are the azura-ui-ux §6 mandates. One
absence with two different wordings on two screens of one product is how a
reader learns to distrust both. `common.dataSource.localSeedHint` is the generic
twin of the module notices that already ship, with the module noun removed
("keine Live-Daten", not "keine Live-Buchungen"), because it is a `common` key
and will be reached for by surfaces that are not ledgers. No em dashes; no
"Seed", which is developer jargon azura-ui-ux §7b bans from anything a property
manager reads.

**`common.notAvailable` is added but NOT verified rendering.** Measured against
the seed: 500 of 500 units carry both a price and an area, across every
`dataQuality` filter, so the branch that renders it never executes on that page
today. It was still missing and still needed adding — the code path is real and a
Supabase-backed row may well have a gap — but nobody should record it as seen.
This also means M-005's only user-visible symptom was ever the banner.

### M-006 is NOT fixed here

It sits between M-005 and M-007 in the report and is a different thing: evidence

`evidence:view` assertion before the repository read in W3-C's page. Out of

### M-007 — `<html lang="de">` on every locale

**Was.** `/en`, `/tr` and `/ru` all served `lang="de"`. Screen readers,
hyphenation, spell-check and translation prompts all read that attribute, so
Russian and Turkish were pronounced with a German voice.

**Why it had survived.** `app/[locale]/layout.tsx` could not fix it: `<html>`
belongs to the root layout and a second nested `<html>` is invalid. W1-C's own
header says exactly that and filed the request rather than reaching across
(SYSTEM-PROMPT §4.1). This is that request, done.

**Fixed by** resolving the locale in `app/layout.tsx`:

```tsx
const locale = await getLocale()
…
<html lang={locale} dir="ltr" suppressHydrationWarning>
```

`getLocale()` resolves through `i18n/request.ts`, which reads the
`X-NEXT-INTL-LOCALE` request header that `proxy.ts` deliberately folds into the
forwarded headers (`absorbIntlRequestHeaders`). So the attribute carries the same
value the page's own messages were loaded with, **by construction**. Parsing the
pathname here would have been a second, independent derivation of the locale, and
the two would eventually disagree.

Non-locale routes — `app/not-found.tsx`, `app/global-error.tsx`, the API tree —
fall back to `defaultLocale`, which is the language their copy is written in, so
`de` there is correct rather than merely a default.

**Bare subtag, not `de-DE`.** `lib/format.ts` maps to regional tags because
`Intl` needs them to choose separators. `lang` does not: WCAG 3.1.1 asks for the
language of the content, and claiming `en-US` would be wrong for a British reader
while `en` is right for both.

### M-008 — four shipped modules advertising themselves as unfinished

**Was.** `pending: true` on `/dashboard/evidence`, `/units`, `/hotel` and
`/reviews`, all of which have a `page.tsx`. Every role's sidebar showed "In
Arbeit" against four working modules, including the inventory screen that carries
acceptance criterion 3.

**Fixed by** deleting the four flags. Nothing else in that file changed.

### M-009 — `deals`, a nav entry that could not lead anywhere

**Was.** The sidebar rendered the lowercase English slug `deals` among German
labels. `dashboard.deals.title` was undefined in all four catalogues, so the
sidebar's `t.has()` fallback degraded the label to the route slug, and
`app/[locale]/dashboard/deals/page.tsx` did not exist.

**Resolved by removing the entry, not by building the module.** The brief allowed
either. Building it would have meant inventing a deals dataset:
`lib/lead-repository.ts` computes `dealTotalsByCurrency` **inside** the
buyer-pipeline summary, so what a "deal" is in this product is already a property
of a pipeline entry and is already rendered on `/dashboard/buyer-pipeline`. A
second screen would have had to fabricate rows to fill itself, which
SYSTEM-PROMPT §2.3 forbids outright. **A nav entry that leads nowhere is a
smaller defect than a screen of invented money.**

`deals` stays a resource: `lib/contracts.ts` and `lib/rbac.ts` are untouched, the
six `deals:*` permissions remain valid, and five roles still hold them. Only the
navigation offer is withdrawn. Re-adding it is one record in the array plus a
`dashboard.deals.title` in four files — the same move every module window made.

The now-unreachable `t.has()` fallback in the sidebar was kept, with its comment
rewritten to say why: the failure it prevents is the entire nav disappearing, and
the next module window will add a route before it adds four translations. What it
is not is a licence to ship an untranslated entry, and there is now a check that
no route reaches it.

## 3. A production defect found while verifying, NOT fixed here

**Any unmatched asset path renders the entire landing page server-side, throws
three `RangeError`s, and then 404s.**

Found because the harness logged three
`RangeError: Incorrect locale information provided` per page load. They are not
from the pages under test — they come from the `/favicon.ico` request Chromium
fires alongside every navigation. Isolated one request at a time:

```
request                      -> status | RangeError count
/                            -> 307   | 0
/de                          -> 200   | 0
/en                          -> 200   | 0
/ru                          -> 200   | 0
/de/hotel                    -> 200   | 0
/de/login                    -> 200   | 0
/favicon.ico                 -> 404   | 3      <-- here
/de/there-is-no-such-page    -> 404   | 0
/icon.png                    -> 404   | 3      <-- and any sibling
/robots.txt                  -> 200   | 0
```

**Mechanism.** `/favicon.ico` does not match the proxy's locale matcher, so Next
matches it against `app/[locale]/page.tsx` with `locale = "favicon.ico"`. The
landing page and its layout render concurrently: `app/[locale]/layout.tsx` calls
`notFound()` for the unknown segment and eventually wins, but not before three
sections have executed with that string as a locale. Reproduced in isolation —
`new Intl.DateTimeFormat("")` and `new Intl.DateTimeFormat("favicon.ico")` both
throw exactly this `RangeError`, while `"de"`, `"en"`, `"tr"`, `"ru"` and
`undefined` all format fine.

The three call sites, each taking `locale: string` and passing it straight to
`Intl`:

```
app/sections/hero.tsx:43          new Intl.DateTimeFormat(locale, …)
app/sections/evidence-band.tsx:65 new Intl.NumberFormat(locale)
app/sections/chrome.tsx:116       new Intl.DateTimeFormat(locale, …)
```

**Pre-existing, and demonstrably not mine.** Those three files are byte-identical
to `origin/main`; F3 changed seven files and none of them is in `app/sections/`,
`proxy.ts` or `app/[locale]/page.tsx`. The same errors were observed against an
older `main` in a different worktree before any of this work started.

**Why it is worth a ticket.** The 404 is correct, but every favicon request costs
a full server-side render of the landing page — including `CoastMaquette` and the
evidence band — and writes three errors into production logs. A crawler or a
monitor hitting `/apple-touch-icon.png` does the same.

**Not fixed here** because the fix belongs in `proxy.ts` (excluding asset-like
paths from the locale matcher), and changing that matcher touches the CSP and
locale routing a great deal depends on. That is not a change to make at the end
of a defect-fix task under the heading of a different ticket. Two candidate
fixes, in order of preference:

1. Exclude asset-shaped paths from the proxy matcher, so they never reach the
   `[locale]` segment. Fixes the class.
2. Make the three sections take `locale: Locale` and route through
   `intlLocale()` from `lib/format.ts`, which already owns the app-locale →
   BCP-47 mapping. Fixes the crash but still renders the page.

Both are worth doing; (1) alone is enough to stop the waste.

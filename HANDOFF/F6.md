## 1. Job 1 — F1-002, the `RangeError`

### Reproduced before anything was changed

Built the tree untouched, ran `next start`, and asked for the four locales plus
the segments a browser and a crawler actually request:

```
/de 200  /en 200  /tr 200  /ru 200
/xx 404  /favicon.ico 404  /robots.txt 200  /.well-known 404
/index.php 404  /apple-touch-icon.png 404

RangeError count in the production log: 12
```

Three distinct throw sites per request, from the **production** log:

```
⨯ RangeError: Incorrect locale information provided
    at new DateTimeFormat  → app/sections/hero.tsx
    at new NumberFormat    → app/sections/evidence-band.tsx
    at new DateTimeFormat  → app/sections/chrome.tsx
```

**F1-002 named two of those three.** `chrome.tsx` was throwing too and no report
mentions it.

### The trigger is not an exotic locale

Measured directly, on this Node:

| passes | throws |
| --- | --- |
| `de` `en` `tr` `ru` `xx` `wp-admin` `de-DE` | `favicon.ico` `robots.txt` `index.php` `.well-known` `apple-touch-icon.png` `sitemap.xml` `de_DE` `de-` `de.DE` `en US` `""` `" "` `a` `123` `%20` `..` |

`Intl` rejects anything that is not a **structurally** well-formed language tag.
An unknown-but-well-formed locale like `xx` is fine. What throws is every
root-level asset path a browser requests on its own initiative.

**The response was a 404 the whole time**, because `app/[locale]/layout.tsx`
calls `notFound()` and wins the race against the page. That is why nobody saw a
broken page. The page function still threw, in production, on every one of those
requests, and it is one refactor of that layout away from being a 500.

### The scope was six times the report

F1-002 named 2 call sites. Grepping for the *shape* rather than trusting the
report found **30 sites across 18 files**, every one passing either a raw route
segment or an unvalidated `params` field straight into `new Intl.*()`.

A detail worth keeping: most dashboard pages declare `params: Promise<{ locale:
Locale }>`. That declaration is a promise about the URL **that the URL never
made** — Next hands the raw segment through and TypeScript believes the
annotation. `app/[locale]/dashboard/calendar/page.tsx` was the one page already
doing it correctly, via `intlLocale(locale)`.

### The fix

`apps/web/lib/format.ts`, which already owned the locale→tag map:

```ts
export function isLocale(value: unknown): value is Locale
export function intlLocaleTag(value: string): string   // never throws
```

`intlLocaleTag` narrows a known locale to its pinned tag and degrades anything
else to the default locale's tag. It then re-verifies the result through
`Intl.getCanonicalLocales`, which looks paranoid and is not: `INTL_LOCALE` is
hand-maintained, and a locale added to `CONTRACTS.md` §7 without an entry here
yields `undefined` while a typo yields a malformed tag. Either would put the
original `RangeError` back inside the one module whose purpose is that it cannot
happen. Cached per distinct input.

All 30 call sites now go through it. **Zero raw sites remain** (`grep` for
`new Intl.*(locale)` outside `format.ts`: 0).

### Fixing the tag mattered as much as not throwing

`new Intl.DateTimeFormat("en")` does not throw. It formats in the runtime's
default order, not the one W1-C pinned. Under `next start`, per locale:

| locale | dates rendered | numbers |
| --- | --- | --- |
| `de` | `27.07.2026` | `1.000` `15.000` |
| `en` | **`07/27/2026`** | `1,000` `15,000` |
| `tr` | `27.07.2026` | `1.000` |
| `ru` | `27.07.2026` | locale separators |

`en` is the US order W1-C specified. Before this change those thirty sites were
formatting on `de`/`en`/`tr`/`ru` rather than `de-DE`/`en-US`/`tr-TR`/`ru-RU`.

### Verified, and one measurement that does NOT prove what it looks like

After the fix, clean `.next`, rebuild, `next start`, same probe set:

```
/de 200  /en 200  /tr 200  /ru 200
/xx 404  /favicon.ico 404  /robots.txt 200  /.well-known 404
/index.php 404  /apple-touch-icon.png 404  /de_DE 404  /de- 404  /wp-admin 404

RangeError count in the production log: 0        (was 12)
```

**That number does not isolate my change, and I will not claim it does.** The
concurrent window added a `notFound()` to `app/[locale]/page.tsx` at 09:54,
before I took this measurement, and it returns before any section renders. On
this tree the sections are never reached for a bad locale, so 0 is the two
changes together.

So the guard is proved separately and exhaustively, in
`scripts/locale-guard-probe.mts`:

```
── the corpus still throws when passed raw, which is the defect
   19 of 23 inputs throw when passed raw
── the guard never throws, and what it returns is always usable
── an unrecognised locale degrades to the default, it does not guess
── control: the four real locales are NOT degraded
── control: the pinned tags are the ones W1-C specified
   en → 07/27/2026
── isLocale is a real check, not a cast

143 pass · 0 fail
```

Every returned tag is fed back into all three `Intl` constructors, because a
guard that returns a value nothing can use has moved the crash rather than
removed it.

## 2. Job 2 — the object-level gate already exists, and it works

The brief asked me to extend `seed-cross-currency-ratio` to reason over the
object, and to prove it against the shape `HANDOFF/F2.md` §7.4 named:

```ts
{
  title:   "F-002 · 1+1 Einstiegspreis: 2,1-fache Spanne über vier Portale",
  summary: "Haspo EUR 112.000, Seaside EUR 185.000, Housearch USD 239.171.",
}
```

**That check is already implemented in this worktree**, as
`seed-record-cross-currency-ratio` in `scripts/verify-evidence.mjs`, by the
concurrent window described at the top. It groups prose fields by the record
they sit in via brace matching, unions the currencies across the whole record,
and applies the same one-currency escape hatch the other rules use. It also
divides labour deliberately: a ratio whose own string already names two
currencies is left to `seed-cross-currency-ratio`, so one defect produces one
violation.

**I did not write a second copy.** Two implementations of one rule is the drift
risk W0-B already flagged about `assertFactInvariants`, and duplicating it into a
file another process is actively writing would be worse than useless.

What I did instead is the half the brief asked for that had not been done:
**prove it.** Restoring the record verbatim, plus two variants and a control:

| case | exit | rule |
| --- | --- | --- |
| F2 §7.4 verbatim: multiplier in `title`, amounts in `summary` | 1 | **FIRED** |
| the same split, English, `factor of` with no `x` | 1 | **FIRED** |
| reversed: amounts in `title`, multiplier in `summary` | 1 | **FIRED** |
| **control**, must pass: ratio scoped to one currency, both named in the record | 0 | silent |

```
restore byte-identical: True | validator on restored file: exit 0
OBJECT GATE REJECTS THE SHAPE F2 COULD NOT SEE
```

The reversed case matters: it is not the shape anyone wrote down, and the gate
catches it because it reasons about the record rather than about the sentence
somebody remembered.

### The gap that is still open, and it is the one the brief is pointing at

> *"Every overclaim we have shipped was caught by a person reading, and the gates
> only cover what someone already thought to check."*

`SEED_FILES` is one file:

```js
const SEED_FILES = [path.join(ROOT, "apps", "web", "lib", "evidence-data.ts")];
```

**`messages/{de,en,tr,ru}.json` is scanned by no gate at all** — `grep -n
"messages" scripts/verify-evidence.mjs` returns nothing. That is where every
user-visible string in the product lives, in four locales, and F2 already had to
fix one overclaim in it by hand: `dashboard.listings.compare.findingNote`
described a `2.1x` cross-currency spread. A `title` / `summary` pair written
there would be exactly the shape job 2 is about, on the surface a client
actually reads, with nothing checking it.

I measured whether it is live before proposing work:

```
de: 1836 strings, 0 carry a ratio token
en: 1836 strings, 0 carry a ratio token
tr: 1836 strings, 0 carry a ratio token
ru: 1836 strings, 0 carry a ratio token
```

**Zero live instances** — F2's fix removed the last one. So this is preventive,
not urgent, which is why I am reporting it rather than racing another window to
patch it into a file it is mid-edit on. The extension is small: add the four
catalogues to `SEED_FILES`, and treat each leaf object in the JSON as a record.
It needs one owner and a quiet tree.

The other files with the same exposure and no coverage:
`hotel-data.ts`, `operations-data.ts`, `finance-data.ts`, `portal-data.ts`,
`lead-data.ts`, `communications-data.ts`, `governance-data.ts`,
`document-data.ts`, `inventory-data.ts`, `dashboard-home-copy.ts`. Each is
hand-written, each carries prose next to money.

One thing found in my own output, not in anyone else's: the first version of
`scripts/locale-guard-probe.mts` committed as **`Bin 0 -> 4868 bytes`**. Its
hostile corpus included a NUL, and I had written it as a raw byte rather than
` `, which makes git classify the file as binary. That is SEC-008 exactly:
a NUL hides a file from `git grep -I` and from both secret scanners. Rewritten as
an escape, the file is text again and the corpus is visible in review.

One thing to know about the build: the first `next build` after my edit failed
with `Cannot find name 'isLocale'` and the next one passed. I did not accept
that. A clean build with `.next` and `tsconfig.tsbuildinfo` removed passes from
scratch, and `tsc --noEmit` was green throughout, so the failure was a stale
incremental cache — most likely mid-write by the concurrent window, since
`app/[locale]/page.tsx` references `isLocale` and its mtime sits between my two
builds.

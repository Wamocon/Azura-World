## 1. M-002 — fixed

### Reproduced first, as the brief asked

```
profiles?select=id             -> 200
profiles?select=role           -> 200   {"role":"admin"}
profiles?select=roles          -> 400   42703  column profiles.roles does not exist
profiles?select=anonymized_at  -> 400   42703  column profiles.anonymized_at does not exist

the exact list from lib/auth.ts:152 -> 400  42703
```

`public.profiles` carries **eleven** columns on the live project, and the fifteen migrations create
exactly those. `roles` and `anonymized_at` are in none of them; `roles` appears in four migrations
in comments only.

PostgREST rejects the **whole** request for one unknown column, so `profileError` was non-null on
every authenticated request, `resolveSupabaseProfile` took its `profileReadFailed` branch, and
every user in the product resolved to `tenant`.

**The eleven stored roles were correct all along.** The data was never wrong; only the projection
was. That is what made the fix a one-line change rather than a migration.

### The fix

`CONTRACTS.md` §3 freezes the role list, so the resolution changed and the list did not.

- **`PROFILE_COLUMNS` / `PROFILE_SELECT`** now live in `lib/auth-resolution.ts`, naming only
  columns a migration creates. `lib/auth.ts` imports `PROFILE_SELECT` and passes it to
  `.select()`.
- They live in **`auth-resolution.ts`, not `auth.ts`**, deliberately: `auth.ts` imports
  `next/headers` and cannot be loaded outside a Next runtime, so a projection declared there is one
  no test can import. A projection no test can import is a projection that drifts from the schema
  unobserved, which is the entire history of this defect.
- The two downstream checks were **not** removed. `normalizeRoleList(row.roles, role)` and the
  `anonymized_at` suspension test already tolerate `undefined`; that defensive design was correct
  all along and naming the columns in the projection was the one thing that defeated it. Both now
  carry a comment saying they are inert today and re-arm by themselves the day W1-A adds the
  column **in the same commit as the migration**.

### What this proof does NOT cover, stated plainly

**The session hop.** `supabase.auth.getUser()` needs a signed cookie. The eleven seeded users take
their password from `current_setting('azura.seed_password')`, which was unset, so the seed
generated `encode(gen_random_bytes(24),'base64')` and **no password is recorded anywhere in the
repository**. Minting one is a credential rotation, which is on the unattended never-do list, so
the probe stops at that boundary.

The probe drives the two things SEC-002 actually broke — the projection and the resolution — with
real rows from the live database. The F1 diff is a projection constant and two comments; it touches
nothing on the session path. **Somebody with a password should still sign in once as `admin` and
confirm the sidebar shows 21 entries rather than 12.** That is the one remaining step and it needs
a human with a credential.

### One assertion I got wrong

The probe first tested `degradedReason === undefined` and failed against correct code: a healthy
profile carries `degradedReason: null`. **The assertion was wrong, not the resolver.** Fixed in the
probe and noted there, because the alternative is somebody later "fixing" the resolver to match a
bad test.

## 2. M-006 — retracted, and it was mine

**SEC-003 does not reproduce. The evidence page already guards correctly, and so do all twenty
module pages.**

`evidence/page.tsx` computes `mayView` and returns the refusal at line 117; the `Promise.all` of
`getFinding` / `getPortalListings` / `getSources` starts at line 137. Its own comment says
*"Nothing is fetched for a caller who may not see it."*

### How I got it wrong in W5

My probe counted `/F-002|F-013|Haspo|Widersprüch|competingValues/i` over the whole response.
**`F-002` is in the shipped `evidence` message namespace**, and `getTranslations({ namespace:
"evidence" })` is called by finance, wallet, vendor-invoices and others. So the token appears in
the payload of pages that read no evidence data at all — measured, exactly 3 occurrences on each of
`/dashboard/finance`, `/dashboard/wallet` and `/dashboard/vendor-invoices`.

A substring search over a whole response is not a leak test. The marker has to be something only
the data can produce. This is the same failure mode W4-B recorded about a cached URL containing the
word `dashboard` — which I quoted approvingly in the same report that made the mistake.

### The correct measurement

Visible DOM split from payload, counting only row-producible markers (`Housearch`,
`hasporealty.com`, `238.967`, `snapshotHash`, ledger references, unit ids), across 5 modules × 7
roles = 35 pairs:

```
/dashboard/evidence          all 7 roles   visible=0  payload=1 (catalogue text)  refusal=yes
/dashboard/finance           all 7 roles   visible=0  payload=0
/dashboard/wallet            all 7 roles   visible=0  payload=0
/dashboard/vendor-invoices   all 7 roles   visible=0  payload=0
/dashboard/units             5 roles       visible=0  payload=22
```

**The 22 on `units` are not a leak.** All eleven roles hold `units:view`, and the 22 rows are the
publicly listed units — `units_select_public … using (is_publicly_listed)`, the same 22 W2-D
measured for an anonymous caller and the same ones the public landing page shows.

**Nothing was changed for M-006, because there was nothing to change.** `MANUAL-TEST-REPORT.md` has
been corrected in this branch: the M-006 entry is struck through with the reason, and the §2
verification table now reads NOT REPRODUCIBLE.

## 3. F1-001 (new) — six roles get HTTP 500 on the money pages

**Severity:** Major · **Owner:** W3-D (`components/finance/finance-scope.ts`) + W2-A
(`lib/finance-repository.ts`) · **Not fixed by F1** — reasoning below.

Newly visible **because M-002 is fixed**: roles now resolve to themselves, so pages take
role-specific paths that were unreachable while everyone was `tenant`.

The page's gate and the repository's gate disagree:

| role | `wallet:view` | `finance:view` | `vendor_invoices:view` | repository gate (`level ≥ accountant`) |
| ---- | ------------- | -------------- | ---------------------- | -------------------------------------- |
| staff | yes | no | yes | **no** |
| owner | yes | yes | no | **no** |
| tenant | yes | no | no | **no** |
| service_provider | no | no | yes | **no** |
| child_owner | yes | no | no | **no** |
| child_tenant | yes | no | no | **no** |

`resolveFinanceScope()` admits the role, the page calls the repository, `finance-repository`
answers `forbidden`, and the Server Component has no handler:

```
⨯ Error [RepositoryError]: You do not have access to this data.
    at runRepository (lib\repository-base.ts:281:11)
    at async WalletPage (app\[locale]\dashboard\wallet\page.tsx:105:43)
  apiError: { code: 'forbidden', … }
```

Measured 500s: `wallet` for tenant, owner, staff, accountant · `finance` for owner, accountant ·
`vendor-invoices` for service_provider, accountant · `units` for tenant, owner.

**It is fail-closed. No data leaks.** It is a robustness and UX defect, not a security one: the
user gets an error page where they should get a refusal, or the data.

**Why F1 did not fix it.** The fix requires deciding *who is authoritative* — whether `staff`
should see wallets at all — which is a product decision spanning two other windows' files, and F1's
brief scoped it to M-002 and M-006. Deciding it unattended is exactly what SYSTEM-PROMPT §4.1 and
§6 forbid.

**Recommendation.** Reconcile in one direction and state which:

1. If the repository is authoritative (it is the security boundary and it is RLS-aligned), narrow
   the RBAC permissions so `wallet:view` is not granted to roles the repository will refuse; or
2. if the RBAC matrix is authoritative, widen `isFinanceVisibleRole` and let RLS scope the rows.

Either way, a page that receives `forbidden` from a repository should render the refusal it already
has (`<AccessRefused>`), never propagate to the error boundary.

## 4. F1-002 (new) — `RangeError` in two landing sections

**Severity:** Minor · **Owner:** W3-A

```
⨯ RangeError: Incorrect locale information provided
    at new DateTimeFormat  app\sections\hero.tsx:43:20
    at new NumberFormat    app\sections\evidence-band.tsx:65:18
```

Both construct `Intl.*Format(locale)` with the raw route parameter. A request carrying an
unexpected locale segment takes the landing page to the error boundary. Pre-existing and unrelated
to the F1 change; `lib/format.ts` already has `intlLocale()` for exactly this mapping and these two
call sites do not use it.
